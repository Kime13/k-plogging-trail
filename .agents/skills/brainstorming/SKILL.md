# Brainstorming — 설계 먼저, 구현은 나중

새 기능을 추가하거나 기존 기능을 크게 변경하기 전에, 사용자와 대화하며 요구사항을 확인하고 설계를 확정한다.

<HARD-GATE>
설계를 제시하고 사용자가 승인하기 전까지 코드를 작성하거나 파일을 수정하지 않는다.
"간단해 보여서 설계 없이 바로 한다"는 안 된다 — 간단한 것일수록 가정이 숨어 있다.
</HARD-GATE>

## 체크리스트

1. **프로젝트 컨텍스트 파악** — 관련 파일, AGENTS.md, 최근 커밋 확인
2. **질문으로 요구사항 확인** — 한 번에 하나씩, 가능하면 객관식으로
3. **2-3가지 접근법 제시** — 트레이드오프와 추천안 포함
4. **설계 제시** — 섹션별로 사용자 승인 받기
5. **설계 문서 저장** — `docs/specs/YYYY-MM-DD-<주제>.md`로 커밋
6. **구현 계획으로 전환** — `writing-plans` 스킬 호출

## K-Plogging Trail 자주 묻는 질문

### 새 코스 지역 추가 시

1. 어느 지역? (예: 강원, 경주, 인천…)
2. 몇 개 코스?
3. 테마 종류? (coastal, mountain, park, heritage…)
4. 공식 지도 URL 확보 여부?
5. 카카오맵 URL 확보 여부?

### 새 페이지 추가 시

1. `pages/N_이모지_Name.py` 파일명은?
2. 사이드바 필터가 필요한가?
3. 외부 API 연동이 필요한가?
4. Supabase 테이블이 필요한가?

### API 연동 변경 시

1. 어떤 API? (Gemini, TourAPI, Supabase, OSRM, Kakao)
2. 기존 `claude_api.py`/`tour_api.py` 수정인가, 새 모듈인가?
3. 에러 핸들링 전략은?

## 설계 제시 형식

```
## 🎨 설계안

**목표:** [한 줄]
**접근법:** [선택한 방법과 이유]

### 파일 변경
- 생성: [파일 목록]
- 수정: [파일 목록]

### 데이터 구조
[코스 스키마 변경이 있으면 명시]

### UI 변경
[Streamlit 컴포넌트 변경 사항]

### 검증 방법
[어떻게 확인할 것인지]
```

## 금지 사항

- ❌ 설계 승인 전 코드 작성
- ❌ 한 메시지에 여러 질문
- ❌ YAGNI 위반 (불필요한 기능 추가)
- ❌ 기존 코스 데이터 스키마를 임의로 변경
