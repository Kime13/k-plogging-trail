# Explain Before Act — 작업 전 상황 설명

코드 수정이나 명령 실행 전에 반드시 **상황 파악 → 브리핑 → 실행** 순서를 따른다.

## 적용 시점

- 코스 데이터(좌표, 하이라이트) 수정
- 새 지역·코스 추가
- API 연동 코드 변경
- 여러 파일에 걸친 변경
- 처음 접하는 코드 영역

## 실행 순서

### Phase 0 — 침묵 파악

사용자에게 보고 전. **파일 수정·명령 실행 금지.**

1. 관련 파일 열람
2. 에러 분석 (있으면)
3. 영향 범위 추정
4. 접근법 검토

### Phase 1 — 브리핑 (5줄 이내)

```
## 🔍 상황 파악

**문제:** [한 줄]
**원인:** [어떤 파일이 문제인지]
**범위:** [수정 파일 목록] — 변경 규모 [소/중/대]
**계획:** 1. [1단계] 2. [2단계] 3. [검증]
```

### Phase 2 — 실행

- 간단(1파일, 명백): 브리핑 후 바로 실행
- 복잡(여러 파일, 아키텍처): 사용자 승인 대기

### Phase 3 — 결과 보고

- 변경 내용 요약 + 검증 결과 + 후속 작업

## K-Plogging Trail 주의사항

- `claude_api.py`는 실제 **Gemini API** 사용 — 레거시 네이밍
- `helpers.py`, `kakao_coords.py`는 앱에서 미사용 — 건드리지 않기
- `HIGHLIGHT_COORDS` 키와 `highlights_en` 값은 정확히 일치해야 함
- `.env` 파일은 절대 커밋하지 않음

## 금지 행동

| 금지 | 이유 |
|------|------|
| 파악 없이 바로 수정 | 엉뚱한 파일 수정 위험 |
| 설명 없이 명령 실행 | 사용자가 상황 파악 불가 |
| 완료 후 침묵 | 결과 확인 불가 |
